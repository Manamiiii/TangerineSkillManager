## 3. 本机或 CI 可重复执行的检查

在工程根目录按序运行，任何必要命令失败后先修复，不继续把整轮标为通过：

```sh
npm ci
npm run schema
npm run format:check
npm run typecheck
npm test
npm run audit:source
npm run build
npm run test:desktop
npm run dist -- --config.directories.output=release/candidate
```

schema 重新生成后应核对变更是否预期；新依赖或准备正式发布时另外运行 `npm audit`，核对生产依赖许可证声明。`dist` 使用 `--publish never`，只构建。

然后对刚生成的 Windows portable 文件执行（替换为真实绝对路径）：

```sh
npm run test:desktop -- --packaged "<候选EXE的绝对路径>" --portable
```

需要验证当前公共服务时，再显式执行联网检查：

```sh
npm run test:desktop -- --packaged "<候选EXE的绝对路径>" --portable --public-network
```

后一个命令会在临时配置中保存 HTTPS DNS，查询 Cloudflare、GitHub、SkillsMP 并获取测试公开仓库。它不修改个人 Agent 目录或系统网络设置。普通桌面测试不会请求这些服务。具体范围见 [开发说明](DEVELOPMENT.md)。

现有 `.github/workflows/ci.yml` 的三个系统任务已在代码提交 `b349d66` [运行通过](https://github.com/Manamiiii/TangerineSkillManager/actions/runs/41575874377)，包含单元测试、开发版桌面检查和打包，**没有自动执行便携 EXE 或公网验收**。该 CI 不能代替上面的候选包检查，更不能代替干净用户机器测试。表中的本地 GPL 候选是较早的包，不能把新代码的 CI 结果附会到该包上。

## 4. 干净 Windows 验收

完整步骤、通过标准和结果模板见 [WINDOWS_ACCEPTANCE.md](WINDOWS_ACCEPTANCE.md)。执行者只需候选 EXE 和系统自带功能，不需要源码、Node、npm、Git 或 Agent CLI。

所有场景必须标为“通过 / 失败 / 未执行”，附系统版本、候选 hash、实际现象。输入法、杀毒软件或下载来源造成的问题也如实记录；没有启动成功就不能继续用源码模式替代并报告发行包通过。

## 5. 获得明确发布授权之后

以下事项尚未执行，清单本身不授权执行：

1. 确认待发布提交、版本号、目标平台与本轮证据对应；不能发布另一个未经验证的包。
2. 如重新签名或重建，重新生成 hash 并验收最终文件。校验文件与 EXE 成对交付。
3. 发布说明写清便携版、实际验证系统、签名状态、配置位置、HTTPS DNS 选择、市场实验性状态及恢复方法。
4. 核对下载链接和完整性。GitHub 暂无正式 Release 时返回 `unavailable` 是已测行为，不等于新版本检测和分发已测通过。
5. 只有真实发行版可用后，才能验证版本比较后的用户下载流程；不为测试而擅自创建公开 Release。
6. 本项目采用 `GPL-3.0-only`。每份发行包须包含 LICENSE 和第三方声明；同一下载位置提供与该二进制对应的完整源码（包括构建脚本与锁文件），并验证源码链接可用。不能用持续变化的 main 分支代替该发行版的对应源码。

## 6. 作者可选体验反馈

无需重复跑自动测试。若愿意体验，可关注三个问题：能否迅速找到同步入口；冲突原因是否容易理解；来源、库和目标之间的区别是否清楚。反馈影响后续交互改进，不是阻止助手继续工作的审批环节。
